## Repository layout

```
src/
  PcCore.Protocol/            wire contracts; the only assembly that touches System.Text.Json
  PcCore.Capabilities/        dispatcher, policy, path security, security state, identity/pairing/auth,
                              sessions, input routing, media planning, files, evidence, PC Assistant bridge
  PcCore.Windows/             P/Invoke, Desktop Duplication, Media Foundation, DPAPI, registry, Raw Input
  PcCore.NativeInput/         every Windows input call and the HID client; no project references
  PcCore.InputBroker/         the optional elevated injector; ten operations
  PcCore.Transport.Loopback/  Kestrel on 127.0.0.1: /rpc, /ws, token and Host/Origin guards
  PcCore.Transport.Remote/    Tailscale-bound WebSocket, device authentication, sessions
  PcCore.SecureCapture/       LocalSystem service + worker for Secure Desktop frames
  PcCore.Update/              release manifest, store, plan, staging, journalled swap and rollback
  PcCore.Updater/             the separate updater; its UAC step is the only one PC Core takes in normal use
  PcCore.Host/                composition root, tray, control panel, self-tests, simulator
  driver/NexusHid/            the UMDF2 + VHF source driver (C) and its INF
  Assistant/                  the AI Assistant component: its own solution, projects and tests,
                              kept in the layout it was developed in (see below)
tests/
  PcCore.Tests/               xUnit v3 suite for everything above
android/
  Nexus/                      the Android app: protocol/, net/, data/, remote/, security/, files/, ui/
shared/
  protocol/                   cross-language test vectors, generated by the PC test suite
tools/                        release publishing, Android signing setup, driver validation and the
                              driver install plan
docs/                         guides, research records, design history, assets
```

Two boundaries are enforced by project references, not by convention: `PcCore.Capabilities` does not
reference `PcCore.Windows`, and the loopback transport does not either. A capability cannot tell how
its caller arrived, and a transport cannot control Windows. `PcCore.NativeInput` has no references at
all, because the elevated broker shares it and its dependency surface is part of that process's
threat model.

## Building

PC side (.NET SDK 10; `global.json` pins the feature band):

```bash
dotnet build PcCore.slnx -c Release
```

Android app (JDK 21, Android SDK; the Gradle wrapper is checked in):

```bash
cd android/Nexus && ./gradlew :app:assembleDebug
```

HID driver (Build Tools + WDK). The script builds, stages, stamps and catalogs the package, and stops
before signing or installing anything:

```bash
powershell -ExecutionPolicy Bypass -File tools/validate-driver-package.ps1
```

A complete, signed, versioned release of every component is one command
([updating.md](updating.md#publishing)):

```bash
powershell -ExecutionPolicy Bypass -File tools/publish-release.ps1
```

The AI Assistant component builds separately, from its own directory, because it keeps its own
solution, SDK pin and build settings:

```bash
cd src/Assistant && dotnet build -c Release
```

`TreatWarningsAsErrors` is on for every .NET project **except** the Assistant's, which has its own
`Directory.Build.props` (and its own `<Version>`, currently 0.10.1, separate from the product
version). The product version has a single source: `VersionPrefix` in the root
`Directory.Build.props`. The Android app and the release manifest read it from there.

## Testing

```bash
dotnet run --project tests/PcCore.Tests -c Release
```

Run the suite this way rather than with `dotnet test`. The Microsoft.Testing.Platform build bundled
with `xunit.v3` did not support the server mode this SDK's `dotnet test` drives it with, so
`dotnet test` reported zero tests. `dotnet run` is a first-class xUnit v3 entry point and runs
everything. Add `--filter-class <name>` to run one class.

The Assistant's suite is xUnit v2 on VSTest and is run with `dotnet test`, from its own directory so
that its `global.json` applies rather than the root one, which selects the Microsoft.Testing.Platform
runner:

```bash
cd src/Assistant && dotnet test
```

Some of its tests drive real windows on the desktop, so they want a session nobody else is typing in,
and from a terminal that is not elevated: `PcAssistantItselfIsNotElevated` fails in an elevated one.
The live suites skip themselves unless opted into with `PCASSISTANT_REAL_CLAUDE=1`,
`PCASSISTANT_NATIVE_SMOKE=1` or `PCASSISTANT_ELEVATION_LIVE=1`.

Android unit tests (JVM):

```bash
cd android/Nexus && ./gradlew :app:testDebugUnitTest
```

Android instrumented tests. These need an emulator or a device, because they cover the Android
Keystore, MediaStore and FileProvider, which a JVM stub cannot meaningfully exercise:

```bash
cd android/Nexus && ./gradlew :app:connectedDebugAndroidTest
```

There is no CI. Tests run locally before each commit, and commit messages record the counts.

## Self-tests on real hardware

Unit tests cannot answer whether *this* machine's camera produces frames or whether Windows really
routes a HID report to a UAC prompt. PC Core has a set of self-tests that run against real devices
and print measurements:

| Command | What it proves |
|---|---|
| `--selftest-remote-control` | display capture and encoding, pointer injection, indicator modes |
| `--selftest-video` | H.264 encoder, conversion and pacing figures; `--bitrate-change` checks in-place bitrate, `--still-refresh` what repeating a still picture costs, `--gpu-scale` the GPU video processor against the CPU converter |
| `--selftest-native-input` | typing into a real window, touch injection, attribution while armed |
| `--selftest-secure-capture` | a real consent prompt photographed through SecureCapture |
| `--selftest-security` | real hooks, attribution, camera and microphone evidence, digests; `--prompt-hello` |
| `--selftest-live-sensors` | camera and microphone frame counts, rates and time to first frame |

```bash
PcCore.Host.exe --selftest-live-sensors
```

Several real defects were found this way that the unit suite could not see. The commits that fixed
them say so.

## Calling PC Core locally

Start PC Core from a terminal to see its console output:

```bash
dotnet run --project src/PcCore.Host
```

It binds `http://127.0.0.1:47811`, prints a per-run session token, and writes it to
`%LOCALAPPDATA%\PcCore\session.token`. The control panel at that address has the token injected, so
nothing needs pasting.

Every request is one envelope. `POST /rpc` handles request/response; `GET /ws` carries the same
envelopes plus server-pushed events.

```bash
curl -s http://127.0.0.1:47811/rpc -H "Content-Type: application/json" -H "X-PcCore-Token: <token>" -d "{\"protocol_version\":1,\"id\":\"1\",\"type\":\"request\",\"action\":\"system.get_info\"}"
```

```json
{ "protocol_version": 1, "type": "event", "event": "security.state_changed",
  "payload": { "previous_state": "OWNER_PRESENT", "current_state": "ARMED" },
  "timestamp_utc": "..." }
```

Errors are stable codes (`not_authorized`, `invalid_parameters`, `invalid_state_transition`,
`access_denied`, …) and never carry paths outside the boundary or secrets. The envelope, versioning
and error rules are in [design/SPEC.md §4](design/SPEC.md). The action list the phone may call is
`CapabilityPolicy` in `PcCore.Capabilities/Abstractions`.

## Protocol vectors

`shared/protocol/protocol-vectors.json` is generated from PC Core's own implementations and asserted
by both the C# and Kotlin test suites, so the two halves cannot drift apart quietly. It covers
envelopes, pairing payloads, authentication and enrolment proofs, credential fingerprints, owner
sessions, stream frame headers, input shapes, incident summaries and security enums, update results,
and file and clipboard shapes. It exists because an unpinned enum once broke three security features
at once while both sides logged success.

Regenerate it deliberately:

```bash
PCCORE_WRITE_VECTORS=1 dotnet run --project tests/PcCore.Tests -c Release --filter-class "PcCore.Tests.Protocol.ProtocolVectorTests"
```

Then run the Android tests and expect them to fail until the Kotlin side agrees.

## Developing without a phone

The control panel includes a development phone simulator that pairs and authenticates with a
credential held in page memory only. From the command line:

```bash
dotnet run --project src/PcCore.Host -- --simulate-phone-enroll NEXUS2....
```

```bash
dotnet run --project src/PcCore.Host -- --simulate-phone ws://100.x.y.z:47812/nexus
```

`--simulate-phone-enroll` pairs the way a real phone does, over the Tailscale transport, proving
possession of the pairing secret. `--simulate-phone-pair` pairs over loopback with the v1 code. Both
store the simulated phone's credential DPAPI-protected. `--simulate-phone` then runs a full
conversation: authenticate, confirm `DEVICE`, call allowed actions, arm, receive the event, disarm,
confirm a device-management call is denied, and reconnect.

## Conventions

- **Say why.** Comments and commit messages explain the reason and the evidence, especially for a
  decision that looks wrong at first glance. The research records in `docs/` exist for the same
  reason.
- **Measure before claiming.** A number in a comment or a doc was measured, and on which machine is
  stated.
- **Fail closed.** Unknown state, an unresolvable path, a missing authority or an older client all
  mean "no".
- **Nothing sensitive in logs.** Identifiers yes, credentials never.
- **Runtime state never lives in the repository.** `.gitignore` carries a second line of defence for
  state, keys, signing material and diagnostic captures.
